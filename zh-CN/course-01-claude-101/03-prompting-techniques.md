# 单元 3：提示词技巧

## 概述

提示词（Prompt）是你与 Claude 交流的方式。提示词的质量直接决定了 Claude 回复的质量。本单元将介绍编写高效提示词的核心技巧，帮助你从 Claude 获得更好的结果。

> **核心原则：** 提示词写作的本质是清晰的沟通。想象你在向一个聪明但对你的具体情况一无所知的新同事布置任务。

---

## 技巧一：清晰具体的指令

### 问题：模糊的请求

当你的提示词太模糊时，Claude 不得不猜测你的意图，结果往往不是你想要的。

**对比示例：**

| 模糊的提示词 | 具体的提示词 |
|-------------|-------------|
| "帮我写封邮件" | "帮我写一封给客户的道歉邮件，因为项目交付延迟了一周。语气要诚恳专业，300 字以内" |
| "分析这个数据" | "分析这份销售数据中 2024 年 Q3 的趋势，找出销售额下降最多的三个产品类别，并给出可能的原因" |
| "修改这段代码" | "修改这段 Python 代码，让它能处理空列表的情况而不报错，并添加类型注解" |

### 具体化的维度

编写具体的提示词时，可以从以下维度考虑：

```
1. 任务（做什么）     → "帮我写一份项目提案"
2. 主题（关于什么）   → "关于公司内部知识管理系统的升级"
3. 格式（怎么呈现）   → "使用 Markdown 格式，包含大纲和预算表"
4. 长度（多少内容）   → "2000 字左右"
5. 风格（什么语气）   → "正式但不生硬，适合向管理层汇报"
6. 受众（给谁看）     → "目标读者是非技术背景的高管"
```

**综合示例：**

```
请帮我撰写一份项目提案，内容是关于公司内部知识管理系统的升级。
要求：
- 使用 Markdown 格式
- 包含：项目背景、目标、技术方案、时间表、预算估算
- 2000 字左右
- 语气正式专业，适合向管理层汇报
- 目标读者是非技术背景的高管，避免过多技术术语
```

## 技巧二：提供充分的上下文

### 为什么上下文很重要？

Claude 没有关于你的任何背景信息。每段对话对 Claude 来说都是一个全新的开始。提供上下文能让 Claude 更好地理解你的需求。

### 上下文的类型

**1. 背景信息**

```
我是一名初级前端开发者，刚从 JavaScript 转到 TypeScript。
请帮我把下面这段 JavaScript 代码转换成 TypeScript，
并解释你添加的每个类型注解：

function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
```

**2. 目的和约束**

```
我要在明天的团队周会上做一个 5 分钟的汇报。
请帮我整理以下工作内容为一个简洁的演讲大纲：

- 完成了用户登录模块的重构
- 修复了 3 个线上 Bug
- 开始了支付功能的设计
- 和产品团队确认了下季度的优先级
```

**3. 参考示例（Few-shot Prompting）**

提供一两个示例，让 Claude 理解你期望的格式和风格：

```
请按以下格式为我的 API 端点编写文档：

示例：
### GET /api/users
**描述**：获取所有用户列表
**参数**：
- `page` (可选): 页码，默认 1
- `limit` (可选): 每页数量，默认 20
**响应**：
```json
{
  "users": [...],
  "total": 100
}
```

现在请为以下端点编写文档：
- POST /api/orders（创建新订单）
- GET /api/orders/:id（获取订单详情）
- PUT /api/orders/:id/status（更新订单状态）
```

## 技巧三：角色设定

### 什么是角色提示（Role Prompting）？

你可以让 Claude 扮演特定角色，从而获得更专业、更有针对性的回答。

### 角色设定示例

**示例 1：技术面试官**

```
你是一位资深的后端工程师面试官，有 10 年 Java 开发经验。
请就以下话题对我进行模拟面试：
- Java 并发编程
- 数据库优化
- 系统设计

请逐一提问，等我回答后再给出评价和追问。
```

**示例 2：写作教练**

```
你是一位专业的非虚构写作教练。请审阅我的文章草稿，
从以下方面给出反馈：
- 结构是否清晰
- 论点是否有说服力
- 语言是否简洁有力
- 开头是否吸引人

请先给出整体评价，再逐段提出具体修改建议。
```

**示例 3：产品经理顾问**

```
你是一位经验丰富的 SaaS 产品经理。
我正在设计一个面向中小企业的项目管理工具。
请帮我评估以下功能优先级，从用户价值和开发成本两个维度进行分析：

1. 看板视图
2. 甘特图
3. 时间追踪
4. 团队聊天
5. 自动化工作流
```

### 角色设定的最佳实践

| 要点 | 说明 |
|------|------|
| 明确专业背景 | "10 年经验的数据工程师"比"技术专家"更具体 |
| 定义交互方式 | "请先提问再给建议"或"直接给出方案" |
| 设定约束条件 | "只使用免费开源工具"或"预算在 5000 元以内" |
| 指定输出风格 | "用通俗的语言"或"使用学术论文的语气" |

## 技巧四：逐步引导

### 分解复杂任务

面对复杂任务，与其一次性给出所有要求，不如分步引导 Claude 完成。

**方法一：在一条消息中列出步骤**

```
请帮我分析这份用户反馈数据，按以下步骤进行：

第一步：将反馈按主题分类（功能请求、Bug 报告、用户体验、其他）
第二步：统计每个类别的数量和占比
第三步：找出每个类别中提及频率最高的前 3 个问题
第四步：基于分析结果，给出产品改进的优先级建议

[粘贴反馈数据]
```

**方法二：使用多轮对话逐步推进**

```
第一轮对话：
用户：我想构建一个个人博客网站。请先帮我选择技术栈，
     考虑因素：免费托管、简单维护、支持 Markdown。

第二轮对话：
用户：好的，我选择 Next.js + Vercel。现在帮我设计网站的页面结构。

第三轮对话：
用户：页面结构确定了。请帮我写首页的代码。

第四轮对话：
用户：首页完成了。接下来写博客文章列表页。
```

### 使用思维链（Chain of Thought）

你可以要求 Claude 在回答前先展示思考过程：

```
请分析以下业务场景，在给出最终建议前，先展示你的分析过程：

我们的电商平台最近三个月的转化率从 3.2% 下降到 2.1%，
同期流量增长了 40%。可能的原因是什么？应该如何排查？

请先列出你考虑的所有可能因素，逐一分析，最后给出排查计划。
```

## 技巧五：指定输出格式

### 为什么格式很重要？

指定输出格式可以让 Claude 的回答更结构化、更容易使用。

### 常见格式要求

**Markdown 表格：**

```
请用表格比较 PostgreSQL、MySQL 和 MongoDB，
列出以下维度：数据模型、适用场景、性能特点、学习难度、社区活跃度。
```

**JSON 格式：**

```
请将以下产品信息整理为 JSON 格式：

产品名：智能台灯
价格：299 元
颜色：白色、黑色
功率：12W
特点：色温可调、定时关灯、APP 控制

输出格式：
{
  "name": "...",
  "price": ...,
  "colors": [...],
  "specs": {...},
  "features": [...]
}
```

**编号列表：**

```
列出提高代码质量的 10 个实践，使用编号列表。
每条包括：一句话标题 + 两句话解释 + 一个具体示例。
```

**分段结构：**

```
请用以下结构回答：

## 问题定义
[描述问题]

## 原因分析
[分析根因]

## 解决方案
[给出方案]

## 实施步骤
[列出步骤]
```

## 常见误区与解决方法

### 误区 1：一次性问太多问题

```
不好的做法：
"帮我写一个网站，要有用户注册、登录、个人主页、
博客系统、评论功能、管理后台、API 接口，
用 React + Node.js + PostgreSQL，要有测试和部署配置。"

更好的做法：
先从整体架构开始，然后逐个功能模块推进。
```

### 误区 2：假设 Claude 知道你的背景

```
不好的做法：
"按照之前讨论的方案修改代码。"
（如果是新对话，Claude 不知道"之前的讨论"）

更好的做法：
"按照微服务架构方案修改代码，将用户模块和订单模块分离，
使用 REST API 通信。这是当前的代码：[粘贴代码]"
```

### 误区 3：只说"不要做什么"而不说"要做什么"

```
不好的做法：
"帮我写文案，不要太正式，不要用网络用语，
不要太长，不要用难懂的词。"

更好的做法：
"帮我写一段 100 字的产品介绍文案，
语气轻松友好但专业，面向 25-35 岁的职场人士。"
```

### 误区 4：不迭代就放弃

```
第一次结果不理想时，不要直接放弃。
应该通过追问来改进：

用户：这不太对，我需要更具体的建议。
     特别是关于预算有限的情况下如何选择。

用户：方向对了，但请更加注重实操性，
     每个建议附上一个真实案例。
```

### 误区 5：忽略了文件上传功能

```
不好的做法：
手动复制粘贴大段的代码或文档内容

更好的做法：
直接上传文件，然后引用：
"请分析我上传的这份 CSV 数据文件，找出异常值。"
```

## 提示词迭代策略

### 迭代的基本流程

```
┌─────────────┐
│ 写初版提示词  │
└──────┬──────┘
       ↓
┌─────────────┐
│ 查看 Claude  │
│ 的回复       │
└──────┬──────┘
       ↓
┌─────────────┐     ┌─────────────┐
│ 是否满意？   │──否→│ 调整提示词   │──→ 返回第一步
└──────┬──────┘     └─────────────┘
       ↓ 是
┌─────────────┐
│ 完成！       │
└─────────────┘
```

### 迭代的常见调整

| 问题 | 调整方向 |
|------|---------|
| 回答太笼统 | 添加具体要求和约束条件 |
| 回答太长 | 指定字数限制或要求精简 |
| 格式不对 | 提供输出格式示例 |
| 语气不合适 | 明确指定语气和目标受众 |
| 遗漏关键信息 | 在提示词中明确列出需要覆盖的要点 |
| 回答太浅 | 要求"深入分析"或"请展开说明" |

### 实际迭代示例

```
第一次：
用户：帮我写一个 Python 数据处理脚本。

→ 太模糊，Claude 可能生成一个通用示例

第二次（加入具体需求）：
用户：帮我写一个 Python 脚本，从 API 获取天气数据
并存储到 SQLite 数据库中。

→ 好多了，但可能缺少一些细节

第三次（加入细节和约束）：
用户：帮我写一个 Python 脚本，功能如下：
1. 使用 requests 库从 OpenWeatherMap API 获取天气数据
2. 解析 JSON 响应，提取温度、湿度、风速
3. 存储到 SQLite 数据库的 weather_records 表中
4. 添加错误处理和日志记录
5. 支持定时执行（每小时一次）
6. 代码需要有注释和类型注解

→ 非常具体，Claude 能生成符合要求的完整代码
```

## 关键要点

- **清晰具体**：从任务、主题、格式、长度、风格、受众六个维度具体化你的需求
- **提供上下文**：告诉 Claude 你的背景、目的和约束条件；提供示例帮助 Claude 理解你的期望
- **角色设定**：让 Claude 扮演特定角色，能获得更专业和有针对性的回答
- **逐步引导**：复杂任务分步完成，利用思维链让 Claude 展示推理过程
- **指定格式**：明确告诉 Claude 你期望的输出格式（表格、JSON、列表等）
- **避免误区**：不要一次问太多、不要假设 Claude 知道你的背景、要说"做什么"而不只是"不做什么"
- **持续迭代**：提示词写作是一个迭代过程，通过多轮对话逐步逼近理想结果
